Clase 8

Modelado de Datos: Embebido vs Referencias

Objetivos de Aprendizaje
1

Entender la diferencia entre un modelo de datos embebido (desnormalizado) y uno referenciado (normalizado).

2

Identificar cuándo es conveniente embeber datos y cuándo se debe usar referencias manuales o $lookup.

3

Diseñar esquemas BSON eficientes para relaciones 1:1, 1:N y N:M.

1Conceptualización de Términos

Modelo Embebido (Embedded Data Models)

En MongoDB, los datos relacionados pueden ser almacenados en un solo documento estructurado. Esto se conoce como datos "desnormalizados" y se aprovecha el poder del modelo de documentos jerárquicos (arreglos y subdocumentos).

Ideal para: Relaciones "contiene un" (1:1 o 1:pocos) o cuando la información relacionada se consulta frecuentemente junto con el documento principal. Evita hacer múltiples consultas.

Modelo por Referencia (Normalized Data Models)

Se almacenan las relaciones entre los datos incluyendo enlaces (referencias) de un documento a otro, similar al uso de claves foráneas en bases de datos relacionales.

Ideal para: Relaciones "1:Muchos" grandes (cuando el tamaño del arreglo excedería el límite de 16MB) o relaciones N:M, o cuando los datos relacionados cambian independientemente y con frecuencia.

Regla General en NoSQL (MongoDB)

"Los datos que se acceden juntos, deben almacenarse juntos." En MongoDB se recomienda favorecer el modelo embebido por defecto, a menos que haya una buena razón para normalizar (por ejemplo, duplicación excesiva de datos modificables frecuentemente o superar los límites de tamaño).

2Ejemplos de Relaciones

1. Relación 1:1 (Embebido)

Por ejemplo, un usuario y su dirección principal. Dado que se consultan juntos, es mejor embeberlo.

{ "_id": "u100", "nombre": "Ana Pérez", "direccion": { // Subdocumento embebido "calle": "Av. Central 123", "ciudad": "San Salvador", "cp": "1101" } }
2. Relación 1:N (Referencias)

Por ejemplo, un publicador y sus libros. Un publicador puede tener millones de libros. Embeberlos haría que el documento supere los 16MB.

// Colección: publicadores { "_id": "pub_01", "nombre": "O'Reilly Media" } // Colección: libros { "_id": "book_99", "titulo": "MongoDB: The Definitive Guide", "publicador_id": "pub_01" // Referencia al publicador }

3Ejercicios de Práctica

Ejercicio 1: Modelado de 1:Pocos

Imagina una aplicación de contactos donde cada contacto tiene un arreglo de 2 o 3 números telefónicos. ¿Usarías embebido o referencia? Escribe el esquema de un documento embebido con un arreglo telefonos.

// Embebido, porque son pocos teléfonos y siempre se piden con el contacto { "nombre": "Carlos", "telefonos": [ "2222-3333", "7777-8888" ] }
Ejercicio 2: Uniendo Colecciones (JOIN)

Supón que usaste un modelo por referencias (colección ordenes y colección clientes). En la orden guardas el cliente_id. ¿Qué etapa del Aggregation Pipeline usarías para unir (hacer JOIN) ambas colecciones?

// Usarías la etapa $lookup { "$lookup": { "from": "clientes", "localField": "cliente_id", "foreignField": "_id", "as": "datos_cliente" } }
Ejercicio 3: Límite de Documento

¿Cuál es el tamaño máximo en megabytes que puede tener un documento BSON en MongoDB? ¿Qué relación tiene esto con no embeber arreglos que crecen indefinidamente (como los logs de un sistema)?

El límite es 16 MB. Por lo tanto, no se debe usar el modelo embebido para arreglos ilimitados o gigantes (como eventos de log por usuario), ya que el documento terminará excediendo este límite (Anti-patrón: Unbounded Arrays).
