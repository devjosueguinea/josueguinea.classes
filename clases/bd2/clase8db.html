1Definición de Conceptos Fundamentales

1. Modelo Embebido (Desnormalizado)

Consiste en almacenar datos relacionados directamente dentro de un mismo documento BSON utilizando subdocumentos o arreglos.

  • Atomicidad: Las operaciones de escritura sobre el documento son atómicas en un solo paso.
  • Velocidad de Lectura: Recupera toda la entidad en una única operación de lectura I/O de disco.
  • Uso ideal: Relaciones "contiene un" (1:1 o 1:Pocos) donde la información se consulta siempre junta.
2. Modelo por Referencia (Normalizado)

Almacena los datos en colecciones separadas e incluye referencias (como el _id o DBRefs) de una colección a otra, similar a las claves foráneas en SQL.

  • Flexibilidad: Evita la duplicación masiva de datos en entidades independientes.
  • Consulta: Requiere múltiples lecturas o el operador $lookup en Aggregation Pipeline.
  • Uso ideal: Relaciones 1:Muchos grandes (1:Zillones) o relaciones N:M dinámicas.
3. El Límite BSON de 16 MB y Arreglos Ilimitados

MongoDB impone un tamaño máximo estricto de 16 MB por documento BSON para garantizar un rendimiento óptimo de memoria RAM y red.

  • Anti-patrón Unbounded Growth: Ocurre al meter elementos infinitos (como logs o comentarios) en un arreglo embebido. El documento romperá el límite de 16 MB.
  • Solución: Cambiar la dirección de la referencia (del hijo hacia el padre) o usar el patrón de cubos (Bucketing).
4. La Regla de Oro NoSQL

A diferencia del modelado SQL orientado a reducir la redundancia a toda costa, en NoSQL el principio rector es el acceso a la información:

"Los datos que se consultan juntos, deben almacenarse juntos."

Favorece el diseño embebido por defecto y normaliza únicamente cuando existan razones justificadas (tamaño, actualizaciones frecuentes o relaciones N:M).

 Seguro e Ilimitado

Casos de Uso Principales
  • Relaciones 1:1 (ej. Usuario y Configuración).
  • Relaciones 1:Pocos (ej. Cliente y Direcciones).
  • Datos leídos juntos con frecuencia.
  • Relaciones 1:Muchos grandes (ej. Editorial y Libros).
  • Relaciones N:M (ej. Estudiantes y Cursos).
  • Entidades que cambian independientemente.

3Patrones de Diseño de Esquemas por Cardinalidad

Relación 1:Pocos (One-to-Few)
Modelo Embebido

Ocurre cuando un documento contiene un número reducido y acotado de subelementos (ej. Un usuario con 2 o 3 números telefónicos).

{ "_id": "usr_10", "nombre": "Elena Gomez", "telefonos": [ { "tipo": "movil", "numero": "7890-1234" }, { "tipo": "trabajo", "numero": "2255-0011" } ] }
Relación 1:Muchos (One-to-Many)
Referencias Manuales

Cuando la entidad hija puede ser muy numerosa (ej. Una empresa con miles de productos), se usa la referencia del _id del padre en los hijos.

// Colección: productos { "_id": "prod_55", "nombre": "Laptop Gamer", "precio": 1200.00, "categoria_id": "cat_tech" // Referencia al padre }
Relación 1:Zillones (One-to-Squillions)
Parent Referencing

Ocurre cuando se generan millones de eventos por entidad (ej. Sensores de temperatura). NUNCA embeber arreglos. Cada lectura referencia al sensor.

// Colección: lecturas_sensor { "_id": ObjectId("64f1a2b3..."), "sensor_id": "sensor_zona_north", "temperatura": 24.5, "fecha": ISODate("2026-09-05T10:00:00Z") }
Relación N:M (Many-to-Many)
Referencias Cruzadas

Estudiantes inscritos en múltiples cursos. Se guarda un arreglo de IDs en uno o ambos lados para permitir búsquedas directas.

// Colección: estudiantes { "_id": "est_007", "nombre": "Sofia Rivas", "cursos": ["cur_bd2", "cur_prog1", "cur_redes"] }

Ejercicio 2 • Relaciones 1:Muchos y $lookup Dificultad: Intermedio
Artículos de Noticias y Comentarios de Lectores

Un periódico digital publica artículos que reciben miles de comentarios. Los comentarios se almacenan en una colección independiente comentarios guardando el articulo_id. Completa la etapa del pipeline de agregación para unir (JOIN) el artículo con sus comentarios:

db.articulos.aggregate([ { "$lookup": { "from": "comentarios", "localField": "_id", "foreignField": , "as": "lista_comentarios" } } ])

¿Qué problema crítico ocurrirá en pocos días y cuál es la solución adecuada según los patrones de MongoDB?
