Operaciones CRUD, claves de partición y claves de agrupamiento en Cassandra

CQL se parece a SQL en su vocabulario, pero Cassandra organiza y consulta los datos con reglas diferentes. Esta clase estudia esas semejanzas y diferencias mediante un ejemplo completo de una plataforma académica.

Resultados de aprendizaje
Ejecutar operaciones Create, Read, Update y Delete con CQL.
Comparar CRUD en Cassandra con operaciones equivalentes en SQL.
Distinguir clave primaria, clave de partición y columnas de agrupamiento.
Diseñar una tabla a partir de las consultas que debe resolver.

1. ¿Qué significa CRUD?

CRUD reúne las cuatro operaciones básicas que una aplicación realiza sobre los datos: crear, leer, actualizar y eliminar. Es un concepto general, no exclusivo de SQL. Cassandra ofrece estas operaciones mediante CQL (Cassandra Query Language), cuyo aspecto familiar facilita el aprendizaje inicial.

Create

Crea una fila o escribe valores mediante INSERT.

INSERT INTO ...
Read

Lee columnas y filas mediante SELECT.

SELECT ... FROM ...
Update

Modifica valores mediante UPDATE.

UPDATE ... SET ...
Delete

Elimina columnas o filas mediante DELETE.

DELETE ... FROM ...
La similitud es principalmente sintáctica. CQL usa palabras conocidas de SQL, pero no convierte a Cassandra en una base relacional. Cassandra no ofrece un modelo basado en relaciones, claves foráneas y JOIN; sus tablas se diseñan para responder consultas concretas de forma distribuida y eficiente.

2. CQL y SQL: parecidos y diferencias

AspectoSQL relacionalCassandra / CQL
OrganizaciónTablas normalizadas y relaciones entre entidades.Tablas desnormalizadas, orientadas a las consultas de la aplicación.
IdentificaciónLa clave primaria identifica la fila; puede ser independiente de la ubicación física.La clave primaria identifica la fila y contiene la clave de partición que determina la distribución.
RelacionesClaves foráneas, integridad referencial y JOIN.No hay claves foráneas ni JOIN de propósito general.
ConsultasEs frecuente comenzar con entidades normalizadas y crear consultas después.Se identifican primero los patrones de consulta y después se crean las tablas.
DuplicaciónLa normalización busca reducirla.La duplicación controlada entre tablas es habitual para optimizar lecturas.
INSERTSuele fallar si ya existe la misma clave primaria.Por defecto funciona como upsert: crea la fila o actualiza la existente.
WHEREPuede filtrar por muchas combinaciones de columnas, especialmente con índices.Las consultas eficientes siguen la clave de partición y el orden de agrupamiento.
TransaccionesSuelen abarcar varias filas y tablas con semántica ACID.Prioriza distribución y disponibilidad; la atomicidad ordinaria tiene un alcance diferente y las condiciones LWT tienen costo adicional.
Error común: diseñar primero una tabla universal y luego esperar que Cassandra responda cualquier consulta con filtros arbitrarios. El enfoque correcto es describir las consultas necesarias y construir una tabla que las haga directas.

3. La clave primaria de Cassandra

Toda tabla CQL necesita una PRIMARY KEY. Esta clave cumple dos tareas: identifica de forma única una fila y describe cómo se distribuyen y ordenan los datos. Se compone de una clave de partición obligatoria y, opcionalmente, una o más columnas de agrupamiento —también llamadas claves de clustering—.

PRIMARY KEY ((curso_id, periodo), fecha_entrega, actividad_id) └──────┬────────┘ └──────────────┬──────────────┘ │ │ CLAVE DE PARTICIÓN COMPUESTA COLUMNAS DE AGRUPAMIENTO determina la partición ordenan y distinguen filas Fila única = curso_id + periodo + fecha_entrega + actividad_id
PARTITION KEY
Clave de partición

Cassandra calcula un token a partir de esta clave para determinar en qué conjunto de nodos se almacena la partición. Todas las filas que comparten la misma clave de partición permanecen juntas en la misma partición lógica.

En el ejemplo, todas las actividades de un curso durante un período se agrupan juntas porque comparten curso_id y periodo.

CLUSTERING COLUMNS
Columnas de agrupamiento

Organizan las filas dentro de una partición. Su orden en la definición de la clave es significativo y permite búsquedas por rango y lecturas ordenadas.

fecha_entrega ordena las actividades y actividad_id distingue dos actividades que tengan la misma fecha.

Tres formas que no deben confundirse
DefiniciónParticiónAgrupamiento
PRIMARY KEY (a)aNinguno; una fila por partición.
PRIMARY KEY (a, b, c)ab, luego c.
PRIMARY KEY ((a, b), c)Compuesta por a y b.c.
Los paréntesis cambian el modelo. En PRIMARY KEY (a, b), solamente a es clave de partición. En PRIMARY KEY ((a, b)), la partición se determina con la combinación de a y b.

4. Tamaño y distribución de las particiones

Una buena clave de partición distribuye la carga de manera relativamente uniforme y mantiene juntas las filas que se consultarán juntas. Una clave con muy pocos valores puede concentrar demasiados datos y solicitudes en algunos nodos; este problema se conoce como partición caliente o hot partition. Una clave excesivamente específica puede producir millones de particiones diminutas y dificultar ciertas lecturas.

Clave deficiente
PRIMARY KEY (estado)

Si estado solo contiene PENDIENTE o PUBLICADA, casi todos los datos se concentran en dos particiones.

Partición sin límite
PRIMARY KEY (curso_id, fecha)

Todas las actividades históricas de un curso crecerían en una sola partición durante años.

Partición acotada
PRIMARY KEY ((curso_id, periodo), fecha)

El período académico actúa como segmento temporal y limita el crecimiento de cada partición.

5. Ejemplo integrador: actividades de una plataforma académica

La plataforma necesita responder esta consulta principal: “mostrar las actividades de un curso y período, ordenadas desde la fecha de entrega más reciente”. A partir de esa consulta se diseña la tabla.

1Crear el keyspace y la tabla
CREATE KEYSPACE IF NOT EXISTS campus
WITH REPLICATION = {
  'class': 'SimpleStrategy',
  'replication_factor': 1
};

USE campus;

CREATE TABLE IF NOT EXISTS actividades_por_curso (
  curso_id uuid,
  periodo text,
  fecha_entrega timestamp,
  actividad_id uuid,
  titulo text,
  descripcion text,
  estado text,
  puntaje decimal,
  PRIMARY KEY ((curso_id, periodo), fecha_entrega, actividad_id)
) WITH CLUSTERING ORDER BY (fecha_entrega DESC, actividad_id ASC);

curso_id + periodo seleccionan la partición. Dentro de ella, fecha_entrega mantiene las actividades ordenadas en forma descendente. actividad_id garantiza unicidad cuando dos actividades tienen la misma fecha.

2Create: insertar actividades
INSERT INTO actividades_por_curso (
  curso_id, periodo, fecha_entrega, actividad_id,
  titulo, descripcion, estado, puntaje
) VALUES (
  11111111-1111-4111-8111-111111111111,
  '2026-C2', '2026-10-20 23:59:00+0000',
  aaaaaaaa-aaaa-4aaa-8aaa-aaaaaaaaaaaa,
  'Modelo de datos CQL',
  'Diseñar una tabla a partir de una consulta',
  'PUBLICADA', 15.0
);

INSERT INTO actividades_por_curso (
  curso_id, periodo, fecha_entrega, actividad_id,
  titulo, descripcion, estado, puntaje
) VALUES (
  11111111-1111-4111-8111-111111111111,
  '2026-C2', '2026-10-27 23:59:00+0000',
  bbbbbbbb-bbbb-4bbb-8bbb-bbbbbbbbbbbb,
  'Práctica CRUD',
  'Ejecutar operaciones con CQL',
  'BORRADOR', 20.0
);

A diferencia de un INSERT relacional típico, CQL no comprueba primero si la fila existe. Si se repite exactamente la misma clave primaria, se actualizan los valores proporcionados: es un upsert. IF NOT EXISTS puede impedirlo, pero usa una transacción ligera y debe reservarse para casos que realmente necesitan esa condición.

3Read: leer una partición y un rango
-- Todas las actividades del curso y período
SELECT fecha_entrega, actividad_id, titulo, estado, puntaje
FROM actividades_por_curso
WHERE curso_id = 11111111-1111-4111-8111-111111111111
  AND periodo = '2026-C2';

-- Actividades a partir de una fecha dentro de la misma partición
SELECT fecha_entrega, actividad_id, titulo
FROM actividades_por_curso
WHERE curso_id = 11111111-1111-4111-8111-111111111111
  AND periodo = '2026-C2'
  AND fecha_entrega >= '2026-10-21 00:00:00+0000';

La consulta proporciona todos los componentes de la clave de partición. Después puede aplicar una condición de rango sobre la primera columna de agrupamiento. Cassandra localiza la partición y recorre filas que ya están almacenadas en orden.

4Update: modificar una actividad
UPDATE actividades_por_curso
SET estado = 'PUBLICADA',
    puntaje = 25.0,
    descripcion = 'Resolver CRUD y justificar la clave primaria'
WHERE curso_id = 11111111-1111-4111-8111-111111111111
  AND periodo = '2026-C2'
  AND fecha_entrega = '2026-10-27 23:59:00+0000'
  AND actividad_id = bbbbbbbb-bbbb-4bbb-8bbb-bbbbbbbbbbbb;

Para actualizar una fila concreta se proporciona su clave primaria completa. Las columnas de la clave primaria no se actualizan con SET; cambiar la fecha de entrega exige eliminar la fila antigua e insertar otra con la nueva clave. Además, UPDATE también tiene comportamiento de upsert: si la clave no existía, puede crear una fila con los valores indicados.

5Delete: eliminar una columna, una fila o una partición
-- Eliminar solamente el valor de una columna
DELETE descripcion FROM actividades_por_curso
WHERE curso_id = 11111111-1111-4111-8111-111111111111
  AND periodo = '2026-C2'
  AND fecha_entrega = '2026-10-20 23:59:00+0000'
  AND actividad_id = aaaaaaaa-aaaa-4aaa-8aaa-aaaaaaaaaaaa;

-- Eliminar una fila completa
DELETE FROM actividades_por_curso
WHERE curso_id = 11111111-1111-4111-8111-111111111111
  AND periodo = '2026-C2'
  AND fecha_entrega = '2026-10-27 23:59:00+0000'
  AND actividad_id = bbbbbbbb-bbbb-4bbb-8bbb-bbbbbbbbbbbb;

-- Eliminar toda la partición del curso en ese período
DELETE FROM actividades_por_curso
WHERE curso_id = 11111111-1111-4111-8111-111111111111
  AND periodo = '2026-C2';

Cassandra registra eliminaciones mediante tombstones. Estas marcas permiten que la eliminación se propague entre réplicas y se retiran posteriormente durante la compactación. Un número excesivo de eliminaciones o valores expirados puede afectar el rendimiento de lectura.

6. Cómo consultar columnas de agrupamiento

Las columnas de agrupamiento funcionan como una secuencia. Para filtrar eficientemente por una columna posterior, normalmente deben estar restringidas las anteriores. En la clave (fecha_entrega, actividad_id), primero se trabaja con fecha_entrega y después con actividad_id.

Consulta alineada con la clave
SELECT * FROM actividades_por_curso WHERE curso_id = ? AND periodo = ? AND fecha_entrega = ? AND actividad_id = ?;

Localiza una partición y sigue el orden de las columnas de agrupamiento.

Consulta no soportada por el diseño
SELECT * FROM actividades_por_curso WHERE estado = 'PUBLICADA';

estado no identifica una partición. Si esta consulta es necesaria, debe diseñarse otra tabla.

Sobre ALLOW FILTERING: forzar una consulta con esta cláusula no corrige un modelo inadecuado. Puede requerir leer muchas filas o particiones para descartar la mayoría. En producción es preferible crear una tabla orientada al patrón de consulta.

7. Una segunda consulta requiere otra tabla

Supongamos que la aplicación también necesita buscar una actividad directamente por su identificador, sin conocer el curso, período o fecha. La tabla anterior no está diseñada para esa consulta. En Cassandra es normal crear una segunda tabla y duplicar los datos necesarios.

CREATE TABLE IF NOT EXISTS actividad_por_id (
  actividad_id uuid PRIMARY KEY,
  curso_id uuid,
  periodo text,
  fecha_entrega timestamp,
  titulo text,
  descripcion text,
  estado text,
  puntaje decimal
);

INSERT INTO actividad_por_id (
  actividad_id, curso_id, periodo, fecha_entrega,
  titulo, descripcion, estado, puntaje
) VALUES (
  aaaaaaaa-aaaa-4aaa-8aaa-aaaaaaaaaaaa,
  11111111-1111-4111-8111-111111111111,
  '2026-C2', '2026-10-20 23:59:00+0000',
  'Modelo de datos CQL',
  'Diseñar una tabla a partir de una consulta',
  'PUBLICADA', 15.0
);

SELECT * FROM actividad_por_id
WHERE actividad_id = aaaaaaaa-aaaa-4aaa-8aaa-aaaaaaaaaaaa;

La aplicación debe mantener ambas representaciones cuando inserta, actualiza o elimina una actividad. Este costo de escritura y duplicación se acepta para obtener lecturas rápidas y predecibles sin JOIN. La decisión debe documentarse para evitar inconsistencias entre tablas.

8. TTL, escrituras condicionales y consistencia práctica

TTL

Con USING TTL, ciertos valores expiran automáticamente después de una cantidad de segundos.

INSERT ... USING TTL 86400;
IF NOT EXISTS

Evita sobrescribir una fila existente, pero activa una transacción ligera basada en consenso y tiene mayor costo.

INSERT ... IF NOT EXISTS;
IF condition

Permite una actualización condicional cuando se necesita comparar el valor actual.

UPDATE ... IF estado='BORRADOR';
No conviertas cada escritura en una operación condicional. Las transacciones ligeras resuelven necesidades específicas de coordinación, pero reducen el rendimiento frente a las escrituras ordinarias. El modelo debe aprovechar la idempotencia y el comportamiento de upsert cuando sea apropiado.

9. Proceso recomendado de modelado

1Escribir la consulta en lenguaje natural

Ejemplo: “listar las actividades de un curso y período por fecha de entrega”.

2Elegir la clave de partición

Debe localizar los datos consultados juntos y distribuir la carga. Se elige (curso_id, periodo).

3Elegir las columnas de agrupamiento

Deben representar el orden y los rangos necesarios. Se eligen fecha_entrega y actividad_id.

4Estimar tamaño y acceso

Se revisan cantidad de filas por partición, crecimiento, frecuencia de lectura y posibles puntos calientes.

5Crear otras tablas para otras consultas

La búsqueda por actividad_id utiliza actividad_por_id; no se fuerza sobre una tabla que no fue diseñada para ella.

10. Práctica de comprensión

Situación

Se requiere consultar las calificaciones de un estudiante dentro de una asignatura y período, ordenadas por fecha de registro. Cada calificación tiene un identificador único, una actividad y una nota.

Reto: identifica la clave de partición, las columnas de agrupamiento y escribe una tabla CQL.

La consulta reúne calificaciones del mismo estudiante, asignatura y período. Esos tres campos forman una clave de partición compuesta. La fecha permite ordenar y el identificador resuelve empates.

CREATE TABLE calificaciones_por_estudiante (
  estudiante_id uuid,
  asignatura_id uuid,
  periodo text,
  fecha_registro timestamp,
  calificacion_id uuid,
  actividad text,
  nota decimal,
  PRIMARY KEY (
    (estudiante_id, asignatura_id, periodo),
    fecha_registro,
    calificacion_id
  )
) WITH CLUSTERING ORDER BY (
  fecha_registro DESC,
  calificacion_id ASC
);
Síntesis

CQL ofrece INSERT, SELECT, UPDATE y DELETE, pero su parecido con SQL no implica el mismo modelo.

La clave de partición decide dónde viven los datos y qué filas se recuperan juntas. Las columnas de agrupamiento organizan las filas dentro de esa partición.

Una tabla Cassandra no intenta responder todas las preguntas. Se diseña para un patrón de acceso conocido, y otra consulta importante puede justificar otra tabla con datos duplicados.
